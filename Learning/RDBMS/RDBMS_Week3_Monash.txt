DOMAIN -> Set of Atomic values (name, data_type, data_format)
Eg -  customer_number domain - 5 character string of the form xxxdd

A RELATION has a HEADING (Schema) and a BODY.
Eg - CUSTOMER (custno, custname, custadd, credlimit)
 
The Heading is a set of attributes.
Each of these attributes has its own domain.
Eg - dom(custno) = customer_number

The RELATION HEADING is represented by the table header (Column names).
Each row in the RELATION BODY is a Tuple.
The RELATION BODY is a Set of Tuples.

A Relation has no duplicate tuples. 
The tuples in it are unordered. 
The attributes within a tuple are also unordered. 
Each value in a tuple is atomic -> It can't be divided further.

FUNCTIONAL DEPENDENCY -> A set of attributes A functionally determines an attribute B if, and only if, 
for each A value, there is exactly one value of B in the relation. It is 
denoted as A  → B

RELATIONAL MODEL KEYS ->
 * A SUPER_KEY of a relation R is an attribute or set of attributes which exhibits only the uniqueness property.
 * No two tuples of R have the same value for the Super key (Uniqueness property)
 * t1[superkey] ≠ t2[superkey] 

 A CANDIDATE_KEY of a relation R is an attribute or set of attributes which exhibits the following properties:
   * Uniqueness property.
   * No proper subset of CK has the uniqueness property
   * i.e., a Candidate Key is a minimal Super Key.
   * One Candidate Key is chosen as the Primary Key. The remaining Candidate Keys are called Alternate Keys. 
 
 A SURROGATE_KEY is an artificially generated, unique identifier for a database record. It is used when the Natural PRIMARY_KEY is too large or cumbersome to handle.

SELECTION OF A PRIMARY KEY
 - A primary key must be chosen considering the data that may be added to the table in the future.
 - PK should be free of 'extra' semantic meaning and security compliant, preferably a single attribute, preferably numeric.

WHY NULL
  - NULL -> is a representation of the fact that there is NO VALUE.
  - VALUE NOT APPLICABLE -> An attribute doesn't apply in a particular tuple(s).
  - VALUE UNKNOWN -> A certain Tuple has an unknown value for a certain Attribute.
  - VALUE DOES NOT EXIST -> A certain Tuple has no value for a certain Attribute.
  - VALUE UNDEFINED ->  A certain Tuple has an undefined value for a certain Attribute.

FOREGN KEY
 - An attribute/s in a relation that exists in the same, or another relation as a PRIMARY_KEY.
 - A FOREIGN_KEY value must either match the full PRIMARY_KEY in a relation or be NULL.

It is not possible to have a Super Key without pt_date AND pt_time since the same patient may get the same treatment at the same time with the same result on different weeks. The patient may also get the same treatment more than once on the same date. Thus, any Super Key must include the pt_date AND pt_time attributes.

A well-designed Relational Database has "Minimal Redundant Data".

A Relational Database is a collection of normalised relations.

Runners may form a team, the runner who registers the team is 
recorded as the team leader. Each team can have up to 5 members 
(runners). Identify the FK(s):
TEAM(team_id, team_name, team_leader)
RUNNER(runner_id, runner_name, team_id)

The first FOREIGN KEY is runner_id. One TEAM may have up to 5 RUNNERS. So it is a 1:N, i.e., 1:1 to 5  relationship. So, the PRIMARY KEY of the One Side (TEAM) is placed as the FOREIGN KEY of the Many Side (RUNNER). 
The second FOREIGN KEY is team_leader. This is because team_leader is the runner_id of the RUNNER that is the Team Leader of the TEAM. 

DATA INTEGRITY - IMPLEMENTATION
ENTITY INTEGRITY -> PK Value must not be NULL AND No duplicate tuple property then ensures that each primary key must be unique
REFERENTIAL INTEGRITY -> The values of FK must either match a value of a full PK in the related relation or be NULL.
COLUMN INTEGRITY -> All values in a given column must come from the same domain (the same data type and range).

NATURAL JOIN
In a NATURAL JOIN, the following happen:
  * A Cartesian Product is taken.
  * The rows where the IDs do not match are deleted.
  * Projection deletes duplicate columns and rows.
